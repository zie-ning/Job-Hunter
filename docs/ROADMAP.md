# Job Hunter — 개발 로드맵

`PRD.md`를 근거로 작성된 실행용 개발 로드맵이다. 총 **Phase 0 ~ Phase 15** (16개 Phase)로 구성되며, 각 Phase 내 체크리스트(`- [ ]`)로 진행 상황을 추적한다. 항목이 끝나면 `- [x]`로 바꾼다.

Phase의 세부 작업이 많아지면 [docs/tasks/](tasks/)에 Task 파일로 분리한다. 규칙은 `.claude/rules/task.md` 참고.

**MVP 한 줄 요약**: 원티드/워크넷 JD를 수집·구조화하고, 이력서와의 벡터 매칭 점수를 자동 계산해 임계치 초과 시 슬랙으로 알리며, 사용자가 JD별 브랜치에서 요청할 때만(온디맨드) LLM 갭분석·RAG 첨삭을 제공하는 서비스. (PRD 2번)

이 저장소는 현재 `PRD.md` 외에 코드가 없는 순수 기획 단계다. 따라서 아래 모든 항목은 미착수(`- [ ]`) 상태에서 시작한다. 이후 이 로드맵을 재생성할 때는 실제 구현 여부를 확인해 완료된 항목을 `- [x]`로 반영해야 한다.

## ⚠️ 착수 전 결정 필요 (PRD 8번 오픈 이슈)

아래 항목은 Phase 0 착수 전에 팀 확인이 필요하다. 괄호 안은 제안 기본값이며, 확정된 결정이 아니다.

- [x] **프론트엔드 프레임워크 선택** — **결정: React (Vite) SPA**. 이유: 백엔드가 FastAPI로 완전히 분리되어 있고 로그인 후에만 쓰는 대시보드형 앱이라 SSR/RSC 이점이 없음. Next.js는 자체 서버 런타임(API Routes/Server Actions)을 포함해 로직이 Next 서버와 FastAPI 양쪽에 흩어질 위험이 있는 반면, SPA는 서버 런타임 자체가 없어 비즈니스 로직이 물리적으로 FastAPI 한 곳에만 존재하도록 구조적으로 강제됨
- [ ] **매칭 점수 임계치 구체값 및 알림 재발송(중복 방지) 정책** — (제안: 초기 임계치는 상위 유사도 분포를 보고 데이터 기반으로 정하고, 동일 JD에 대해 이미 알림을 보냈다면 재발송하지 않는 정책으로 시작) ⚠️ 팀 확인 필요
- [ ] **이력서/JD 임베딩 단위 (전체 문서 vs 섹션별 임베딩)** — (제안: MVP는 전체 문서 단위로 시작, 이후 섹션별 임베딩은 향후 확장으로 미룸) ⚠️ 팀 확인 필요
- [x] **사용자별 데이터 격리 및 권한 모델 상세** — **결정: 모든 테이블에 `user_id` FK + 앱 레벨 권한 체크**. Postgres RLS는 MVP 범위에서 제외(구현 속도 우선), 필요 시 Post-MVP에서 재검토
- [ ] **크롤링 확장 시 대상 사이트 및 정책** — MVP 범위 아님(PRD 5번). Post-MVP에서 재검토 ⚠️ 팀 확인 필요
- [ ] **슬랙 웹훅 설정 방식 (사용자별 개별 웹훅 등록 vs 공통 채널)** — (제안: 사용자별 개별 Incoming Webhook 등록. 이유: 멀티유저 서비스이므로 알림이 개인화되어야 함) ⚠️ 팀 확인 필요
- [ ] **Slack 사용자 ↔ 앱 계정 매핑 방식** — (제안: 브랜치 생성 등 개인화 액션이 필요한 시점에 Slack OAuth로 앱 계정과 1회 연결) ⚠️ 팀 확인 필요
- [ ] **슬랙 내에서 브랜치 base 버전을 어떻게 선택하게 할지** — (제안: MVP는 "지원 준비하기" 클릭 시 웹앱으로 유도해 base 버전을 웹 UI에서 선택하게 하고, 슬랙 내 추가 인터랙션은 Post-MVP로 미룸) ⚠️ 팀 확인 필요 → 웹 UI에서는 브랜치 fork/새로 시작 방식으로 확정됨(Phase 2, PRD 3.3 참고); 슬랙 내부 인터랙션 지원 여부만 아직 미정

## Phase 0: 프로젝트 셋업

**목표**: FastAPI 백엔드, pgvector가 활성화된 Postgres, 프론트엔드 프로젝트가 갖춰져 이후 모든 Phase가 이 위에서 개발될 수 있다.

**선행조건**: 없음 (최초 Phase). 프론트엔드 프레임워크(React Vite SPA)·데이터 격리 모델(user_id FK + 앱 레벨 체크) 확정됨.

**세부 작업**:
- [x] FastAPI 프로젝트 스캐폴딩 (디렉토리 구조, 설정 관리, 환경변수 로딩)
- [x] Postgres + pgvector 확장 인스턴스 프로비저닝 (Supabase, Seoul 리전, Session Pooler 연결 확인 완료, pgvector 활성화 확인 완료)
- [x] DB 마이그레이션 도구 설정 (Alembic, 비동기 템플릿) — `DATABASE_URL` 연결 확인 완료
- [x] 프론트엔드 프로젝트 스캐폴딩 (React + Vite SPA, TypeScript 7)

**완료 기준**: 로컬 환경에서 FastAPI 서버와 React 프론트엔드가 각각 정상 기동되고 서로 통신할 수 있으며, DB에 pgvector 확장이 활성화되어 있다.

**관련 PRD 섹션**: 6번(기술 스택)

**선행조건**: Phase 1(배포 파이프라인)

**세부 작업**:

## Phase 3: 인증

**목표**: 사용자가 회원가입/로그인으로 인증되고, 이후 모든 기능이 `user_id` 기준으로 격리된다.

**선행조건**: Phase 0(DB), Phase 2(로그인/회원가입 화면 mock). 인증 방식 확정됨 — **결정: 카카오 소셜 로그인 전용(이메일/비밀번호 가입 없음) + 자체 JWT 발급**. 카카오는 신원 확인 용도로만 쓰고 세션은 이 서비스가 직접 관리(Access token 30분/메모리 보관, Refresh token 30일/httpOnly 쿠키, Refresh Rotation + 재사용 탐지).

**세부 작업**:
- [x] `User`/`RefreshToken` 테이블 설계 및 마이그레이션 적용 (`kakao_id` 유일 식별자, `user_id` FK 기반 격리 토대 마련)
- [x] 카카오 OAuth 콜백 처리 및 자체 JWT 발급 API 구현 (`POST /auth/kakao/callback`)
- [x] Refresh 토큰 rotation + 재사용 탐지(탈취 의심 시 해당 유저 전체 토큰 즉시 폐기) 로직 구현 (`POST /auth/refresh`)
- [x] 로그아웃 및 보호 라우트용 인증 의존성 구현 (`POST /auth/logout`, `GET /auth/me`)
- [x] 인증 백엔드 API pytest 테스트 작성 (카카오 API를 모킹해 신규가입/프로필 upsert/rotation/재사용 탐지/로그아웃/보호라우트 로직만 검증 — 실제 카카오 서버와의 통신은 미검증)
- [x] 카카오 디벨로퍼스 콘솔에 앱 등록 및 REST API 키 발급 (Redirect URI 등록 포함) — 사용자가 직접 진행
- [x] 실제 카카오 계정으로 로그인 E2E 검증 (브라우저로 인가 URL 접속 → `code` 획득 → 실제 API 호출까지 확인)
- [ ] 로그인/회원가입 화면(Phase 2 mock)의 mock 어댑터를 실제 인증 API로 교체

**완료 기준**: 사용자가 회원가입/로그인할 수 있고, 인증된 사용자만 보호된 API를 호출할 수 있다. (백엔드 로직 구현·모킹 테스트·실제 카카오 계정 연동 검증까지 완료, 프론트엔드 연동만 대기 중)

**관련 PRD 섹션**: 6번(인증)

## Phase 4: 이력서 기본 CRUD

**목표**: 사용자가 이력서를 업로드하고, 구조화된 형태로 편집하며, 저장할 때마다 불변 버전이 쌓인다. 별도의 "마스터 이력서" 엔티티는 없으며, 이 CRUD는 범용 브랜치의 버전 관리로 통합된다(PRD 3.2, 3.3 참고).

**선행조건**: Phase 3(인증), Phase 2(브랜치 상세 편집기/버전 관리 화면 mock)

**세부 작업**:
- [ ] PDF/문서 업로드 API 및 스토리지 연동
- [ ] 업로드 시점 텍스트 파싱 로직 (PDF → 구조화된 텍스트)
- [ ] 브랜치 상세 화면 편집기의 mock 어댑터를 실제 업로드/파싱/저장 API로 교체
- [ ] 저장 시 새 버전 생성 로직 (기존 버전 불변 유지) + 코멘트(선택, 빈칸 허용) 입력 필드
- [ ] 버전 목록(커밋 로그) 화면의 mock 어댑터를 실제 버전 API로 교체 (코멘트 표시, 매칭 점수 변화는 Phase 8/12 이후 연동)
- [ ] 버전 상세보기(이전 버전과의 텍스트 diff 뷰) 화면의 mock 어댑터를 실제 API로 교체

**완료 기준**: 사용자가 PDF를 업로드해 파싱된 텍스트를 에디터에서 수정하고 저장하면 새 버전이 생성되며, 버전 목록에서 코멘트를 확인하고 상세보기에서 diff를 볼 수 있다.

**관련 PRD 섹션**: 3.2, 4.1

## Phase 5: JD 소스 연동 (원티드/워크넷 API 클라이언트)

**목표**: 원티드/워크넷 API를 호출해 JD 원문을 가져오고 저장할 수 있다.

**선행조건**: Phase 0(DB)

**세부 작업**:
- [ ] 원티드 Open API(openapi.wanted.jobs) 연동 클라이언트 구현
- [ ] 워크넷(고용24) 공공데이터포털 Open API 연동 클라이언트 구현
- [ ] JD 원문 저장 스키마 설계: "소스 + 원본 공고 ID"를 식별자로 사용 (소스 간·재게시 간 중복 제거 없음)
- [ ] 사용자 수동 JD 등록 API (자동 수집 파이프라인 밖 공고 대응 — 공고 브랜치 새로 만들기 화면에서 사용, PRD 5번 참고). 원본 공고 ID가 없으므로 시스템이 자체 ID 발급

**완료 기준**: 두 소스 각각에 대해 API를 호출해 JD 원문을 가져와 DB에 "소스+원본 공고 ID" 기준으로 저장할 수 있고, 사용자가 직접 등록한 JD도 저장할 수 있다.

**관련 PRD 섹션**: 5번(데이터 소스), 3.1

- [ ] 이력서 버전 임베딩 생성 함수 (버전 저장 시 1회 자동 실행)

- [ ] pgvector 컬럼 스키마 및 코사인 유사도 쿼리 구현
- [ ] "이력서 1개 ↔ JD 여러 개" 매칭: 유사도 상위 N개 JD 선정 API
- [ ] 매칭 결과 저장 (발송 로직 Phase 9의 입력으로 사용)

**완료 기준**: 특정 이력서 버전에 대해 상위 N개 관련 JD와 매칭 점수를 API로 조회할 수 있다.

**관련 PRD 섹션**: 4.3-a, 3.1, 10번

**완료 기준**: 임계치를 넘는 매칭이 발생하면 슬랙 메시지가 온다.

- [ ] 콜백 수신 시 브랜치 생성/이동 로직 호출 (Phase 11과 연결)

## Phase 11: 브랜치 — 데이터모델/API (공고 브랜치 / 범용 브랜치)

**목표**: 공고 브랜치는 하나의 JD를 겨냥해, 범용 브랜치는 특정 공고와 무관하게 이력서 버전 이력을 독립적으로 관리할 수 있다.

**선행조건**: Phase 4(버전 관리), Phase 10(슬랙 콜백), Phase 2(브랜치 화면 mock)

**세부 작업**:
- [ ] 브랜치 데이터 모델: 종류 구분 필드(공고/범용), 상태 필드(미정/진행중/지원완료/마감 — 범용 브랜치는 미적용). (사용자, JD) 기준 최대 1개 제약은 공고 브랜치에만 적용
- [ ] 공고 브랜치 생성 API: base 선택(기존 브랜치 fork 또는 새로 시작) 로직, 신규 생성 시 상태 기본값 "미정"
- [ ] 범용 브랜치 CRUD API (이름, base 선택)
- [ ] 기본 브랜치 지정/해제 API (범용 브랜치 중 최대 1개만 기본으로 지정 가능)
- [ ] 사용자 수동 JD 등록 API 연동 (공고 브랜치 새로 만들기 화면에서 사용, Phase 5 참고)
- [ ] 기존 공고 브랜치 존재 시 새로 만들지 않고 해당 브랜치로 이동하는 로직
- [ ] 브랜치 상태 변경/목록 필터링 화면의 mock 어댑터를 실제 API로 교체

**완료 기준**: 슬랙에서 "지원 준비하기"를 클릭하거나 웹에서 범용/공고 브랜치를 새로 만들면 브랜치가 생성/이동되고, 상태를 수동으로 변경하거나 상태별로 목록을 필터링할 수 있으며, 범용 브랜치 중 하나를 기본 브랜치로 지정할 수 있다.

**관련 PRD 섹션**: 3.3, 4.1, 7번

## Phase 12: 브랜치 내 매칭 재계산 + 개선도 추적

**목표**: 공고 브랜치 안에서 이력서를 저장할 때마다 그 JD 기준 개선도가 자동으로 갱신된다. 범용 브랜치는 겨냥한 JD가 없으므로 이 매칭 재계산·개선도 추적 대상에서 제외된다.

**선행조건**: Phase 11(브랜치), Phase 8(매칭 로직)

**세부 작업**:
- [ ] 브랜치 내 이력서 수정/저장 시 "경량 매칭 재계산" 자동 실행 (브랜치가 겨냥한 JD 1개만 대상)
- [ ] 브랜치 내 버전 간 점수 변화(개선도) 계산 및 표시 화면의 mock 어댑터를 실제 API로 교체
- [ ] "첨삭하기/피드백 받기" 버튼 UI의 mock 어댑터를 실제 트리거로 교체 (클릭 시 Phase 13 트리거)

**완료 기준**: 브랜치 안에서 이력서를 저장할 때마다 해당 JD 기준 개선도가 갱신되어 화면에 표시된다.

**관련 PRD 섹션**: 3.3, 4.1, 4.3-a(경량 모드), 7번

## Phase 13: 갭분석 에이전트 (온디맨드)

**목표**: 사용자가 브랜치 화면에서 요청할 때만, 그 브랜치가 겨냥한 JD 1개를 근거로 구체적 갭 분석을 생성한다.

**선행조건**: Phase 11(브랜치)

**세부 작업**:
- [ ] "첨삭하기/피드백 받기" 클릭 시 실행되는 온디맨드 API 엔드포인트
- [ ] 구체적 갭 분석 LLM 호출: 이력서 + 브랜치가 겨냥한 JD 1개만 입력 (전체 JD DB 검색 금지)
- [ ] 갭 분석 결과 저장 및 조회 API — 브랜치당 최신 결과만이 아니라 요청할 때마다 쌓이는 내역(히스토리)으로 저장

**완료 기준**: 브랜치 화면에서 버튼을 클릭하면 몇 초~수십 초 내 그 JD에 특화된 갭 분석 결과를 조회할 수 있고, 과거에 요청했던 결과도 내역에서 확인할 수 있다.

**관련 PRD 섹션**: 4.3-b, 3.1, 3.3, 10번

## Phase 14: RAG 첨삭 에이전트

**목표**: 갭 분석 결과를 근거로, 그 JD 1개에 특화된 구체적 첨삭 피드백을 생성한다.

**선행조건**: Phase 13(갭 분석 결과)

**세부 작업**:
- [ ] RAG 첨삭 에이전트: 갭 분석 결과 + 동일 JD 1개를 근거 문서로 사용해 "이 JD 대비 이렇게 수정하면 좋다"는 구체적 피드백 생성
- [ ] 첨삭 피드백에 근거(그 JD의 어떤 요구사항인지) 명시
- [ ] 갭 분석·첨삭 결과 표시 화면의 mock 어댑터를 실제 API로 교체 — "첨삭하기/피드백 받기" 한 번의 요청으로 갭 분석+첨삭 피드백이 한 쌍으로 생성되어 내역에 함께 쌓이며, 화면에서는 "공고 분석"/"이력서 리뷰" 두 탭으로 같은 내역을 구분해 보여줌

**완료 기준**: 갭 분석에 이어 그 JD에 특화된 첨삭 피드백이 근거와 함께 화면에 표시되고, 과거 요청 내역도 탭별로 조회할 수 있다.

**관련 PRD 섹션**: 4.3-b, 4.4, 3.1, 3.3, 10번

## Phase 15: 마무리

**목표**: 서비스가 실제로 배포되어 동작하며, 포트폴리오로서 기술 선택 근거를 설명할 수 있는 완성도를 갖춘다.

**선행조건**: Phase 0~14 전체

**세부 작업**:
- [ ] 전체 파이프라인 통합 테스트 (JD 수집 → 구조화 → 매칭 → 슬랙 알림 → 브랜치 생성 → 갭분석/첨삭)
- [ ] 배포 환경 최종 점검 (무료 티어 한도, pgvector 동작 확인)
- [ ] 면접관이 직접 접속해 시연할 수 있는 데모 시나리오 정리
- [ ] 기술 선택 근거 문서화: pgvector를 쓴 이유, 온디맨드 트리거 설계 근거(비용, PRD 10번), 개선도 측정 설계 의도(PRD 7번) 등
- [ ] 비용 모니터링 확인: 온디맨드 항목(갭분석·첨삭)이 실제로 사용자 요청 시에만 과금되는지 점검

**완료 기준**: 배포된 URL에서 전체 시나리오(JD 알림 → 브랜치 생성 → 첨삭까지)를 처음부터 끝까지 시연할 수 있고, 각 기술 선택의 근거를 설명할 수 있는 문서가 준비되어 있다.

**관련 PRD 섹션**: 1.2, 7번, 10번
